## PO の関与を手順に合わせて修正（2026-11-03）

人間が「成果の確認は今POにもやってもらっているはず」「計画やふりかえりの結果はPOに飛んでないんだっけ？」と確認を求めた。手順を照合した説明に「そこは正しい情報で表現しよう」と回答したため、図とノートを修正した。

- 計画: 開発者が案を作り、開発チームが人間に提示して承認を得る。AI の PO への通常の計画承認依頼はない。仕様の不足が見つかった場合は PO に戻す。承認した計画は PR・レポートに記録し、PO が成果の受け入れ確認時に読む。
- 成果: 開発チームの推薦を受け、AI の PO が仕様・受け入れ条件・スコープなどを確認する。その後、人間が実物を確認して採用を判断する。コードの相互レビューと PO の受け入れ確認は異なる。
- ふりかえり: 開発チームが改善案を示し、人間が採否を判断する。開発チームは承認された手順の改善を反映し、結果・仕様の発見・後続 Issue の案などを PO に申し送る。PO が人間と相談して仕様・Issue・優先順位へ反映する。PO にすべての改善の採否を委ねる説明にはしない。
- 図: 成果の枠内に PO → 人間の順序を示す。ふりかえりから次の計画へ戻る経路には、結果の申し送りと PO による仕様・Issue への反映を置く。計画の例外経路と後日の記録確認はノートで説明する。
- 出典: [dual-implement の手順4・8](../../../.claude/skills/dual-implement/SKILL.md)、[accept-review の手順1・2](../../../.claude/skills/accept-review/SKILL.md)、[finish-issue の手順7・8](../../../.claude/skills/finish-issue/SKILL.md)。説明対象の固定版に対応する本プロジェクト初期コミット `a1f0ab4` の同ファイルにも、計画承認・承認済み計画の参照・PO への申し送りの記載があることを確認した。

## 人間・PO の関与と、開発チームが管理する範囲（2026-11-03）

PO と開発チームの間を線でつなぐ要望に対して、最初は開発チームを上段へ移した。人間から「開発チームは下にあったままの方がよかった」「今人間に伸びている線が、POにも伸びればいい」「下のループ部分をまるっと統括しているイメージ」と修正の意図を受け、次の配置に改めた。

- 上段: 人間と AI の PO が対話する。両者から伸びる共通の線を、下段の開発の流れ全体へつなぐ。
- 下段: 計画・実装と検証・成果確認・ふりかえり・次への反映を囲う枠を置き、その下端に「開発チーム」「この流れ全体の進行・比較・完了を管理」と人物を添える。開発チームは工程の1つや特定の工程だけの担当として描かない。
- 各工程の本文: 計画の承認は人間、成果は PO の受け入れ確認の後に人間が採用を判断、改善の採否は人間、と区別する。共通の線は人間と PO の関与を表し、両者がすべての判断を共同承認する意味ではない。
- 受け渡す内容: PO が Issue・着手条件を整え、成果の受け入れ判定を返す。開発チームは成果の確認を依頼し、完了・ふりかえりの結果を申し送る。上下の配置を変えても、この内容は変わらない。
- Issue の着手は PO が「開発可」を付け、起動係が開発チームを開く手順。共通の線を直接の起動コマンドとは説明しない。計画を通常 PO に承認してもらう手順も追加しない。
- 根拠: `accept-review` 手順4の判定返信、`workflow.md` ステップ2・3の着手、`finish-issue` 手順7・8のふりかえりと申し送り。

## 発表ノート案

画面のすべての文字や線を読み上げず、上段 → Issue → 4工程 → 金色 → 次への反映の順で案内する。

1. 上段の対話: 「まず人間が、AI の PO と何を作るかを相談します。PO はプロダクトオーナーの略です。このプロセスでは、人間も作る方向を判断し、AI の PO が仕様や作業へ具体化します。」
2. Issue: 「今回作る範囲と完成の条件を GitHub Issue にまとめ、着手できる状態になったら開発が始まります。」
3. 4工程: 「下の流れ全体を開発チームが管理します。開発者が計画を立て、実装・検証・レビューを進めます。成果は AI の PO も受け入れ確認します。」
4. 金色の3か所: 「この開発の流れで人間が判断するのが、金色の3か所です。計画を承認する。実物を確認して採用を決める。そして、ふりかえりで改善案を採るか決める。このように人間が関わります。」
5. 次への反映: 「結果を AI の PO に申し送り、次の仕様や Issue に反映します。作って終わりにせず、次の開発につなげます。」

話し方の注意: 「人間は3回クリックするだけ」「人間の関与はこの3か所だけ」とは説明しない。上段の相談や、必要な修正の判断もある。図は通常の流れをまとめており、採用・マージの実行内容の承認などの詳細は後続の実例で示す。

補足: 計画の承認を通常 AI の PO に依頼する手順はない。仕様の不足が見つかった場合には PO に戻して人間と決め直す。承認した計画と確認事項の決着は記録に残り、PO が成果の受け入れ確認時に読む。ふりかえりの全結果を PO が事前承認するわけでもない。PO の受け入れ確認で差し戻しとなった場合は、修正・レビューを経て再確認する。図は通常の進行を示し、詳細な戻り方は後続の工程説明で扱う。

着手の補足: 通常は「開発可」の Issue を起動係が見つけ、開発チームを起動する。Issue の作成だけで未確定の課題まで実装を始めるわけではない。
