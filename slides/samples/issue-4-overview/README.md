- 内容の基準: [仕様2.3](../../../docs/spec.md#23-スクラムの考え方用語との対比) の再計画で合意した説明。
- 目的: 最初に人間・AI の役割と開発の循環を一緒に見せ、後続ページの詳しい説明につなぐ。
- 画面: 人間と AI の PO の対話、4つにまとめた工程、人間の3つの判断、開発チームと開発者、次の開発への改善を示す。既存の紙色・藍色・金色と AI の人物素材を再利用する。人間の素材と図の枠は下記の指摘を反映した。
- この図は全操作の手順書ではない。相互レビュー、AI の PO の受け入れ確認、人間の採用判断の区別は本文に示す。差し戻し・採用後のマージの詳細、スクラムのイベント名との対比は後続ページで説明する案。
- 固定期間のスプリント、独立したスクラムマスター、デイリースクラムはこのプロセスに設けていない。開発チームをスクラムマスターに対応付けない。
- 人間はステークホルダーとして確認し、PO として作る方向や優先順位も判断する。図の AI の PO にすべての責任を移した説明ではない。

## PO の関与を手順に合わせて修正（2026-11-03）

人間が「成果の確認は今POにもやってもらっているはず」「計画やふりかえりの結果はPOに飛んでないんだっけ？」と確認を求めた。手順を照合した説明に「そこは正しい情報で表現しよう」と回答したため、図とノートを修正した。

- 計画: 開発者が案を作り、開発チームが人間に提示して承認を得る。AI の PO への通常の計画承認依頼はない。仕様の不足が見つかった場合は PO に戻す。承認した計画は PR・レポートに記録し、PO が成果の受け入れ確認時に読む。
- 成果: 開発チームの推薦を受け、AI の PO が仕様・受け入れ条件・スコープなどを確認する。その後、人間が実物を確認して採用を判断する。コードの相互レビューと PO の受け入れ確認は異なる。
- ふりかえり: 開発チームが改善案を示し、人間が採否を判断する。開発チームは承認された手順の改善を反映し、結果・仕様の発見・後続 Issue の案などを PO に申し送る。PO が人間と相談して仕様・Issue・優先順位へ反映する。PO にすべての改善の採否を委ねる説明にはしない。
- 図: 成果の枠内に PO → 人間の順序を示す。ふりかえりから次の計画へ戻る経路には、結果の申し送りと PO による仕様・Issue への反映を置く。計画の例外経路と後日の記録確認はノートで説明する。
- 出典: [dual-implement の手順4・8](../../../.claude/skills/dual-implement/SKILL.md)、[accept-review の手順1・2](../../../.claude/skills/accept-review/SKILL.md)、[finish-issue の手順7・8](../../../.claude/skills/finish-issue/SKILL.md)。説明対象の固定版に対応する本プロジェクト初期コミット `a1f0ab4` の同ファイルにも、計画承認・承認済み計画の参照・PO への申し送りの記載があることを確認した。

## PO と開発チームの線（2026-11-03）

人間の「PO と開発チームの繋がりは線で繋がない？後で対応する？」を受け、この見本で接続した。上段を人間・PO・開発チームの配置にし、役割間の受け渡しが中央の工程の矢印と交差しないようにした。

- PO → 開発チーム: 「Issue・受け入れ判定」。PO が仕様・Issue・着手条件を整え、成果を確認した後には判定を開発チームへ返す。
- 開発チーム → PO: 「確認依頼・申し送り」。成果の受け入れ確認を依頼し、完了・ふりかえりの結果を申し送る。
- この2本は役割間で受け渡す内容をまとめた線であり、同時に実行する操作や直接の起動コマンドを意味しない。Issue の着手は PO が「開発可」を付け、起動係が開発チームを開く手順。計画を通常 PO に承認してもらう線は加えない。
- 受け入れ判定の返信は `accept-review` の手順4、着手の流れは `workflow.md` のステップ2・3を根拠とする。

## 発表ノート案

「人間と AI が一緒に進める全体像です。人間は AI の PO と話しながら、何を作るかを仕様・Issue に具体化します。PO と開発チームの間では、Issue や受け入れ判定を渡し、成果の確認依頼や結果の申し送りを受け取ります。上段の2本の矢印は、その受け渡しをまとめて示しています。計画は開発者が作り、開発チームが人間に提示して承認を得ます。実装と開発者どうしのレビューを経て、開発チームが成果を推薦します。AI の PO が欲しかったものになっているかを仕様・受け入れ条件に照らして確認し、その後、人間が実物を確認して採用を判断します。採用・マージを経たふりかえりでは、開発チームの改善案を人間が判断します。承認された手順の改善は開発チームが反映し、結果や次の課題は PO に申し送ります。PO がそれを次の仕様・Issue に反映し、次の開発につなげます。」

補足: 計画の承認を通常 AI の PO に依頼する手順はない。仕様の不足が見つかった場合には PO に戻して人間と決め直す。承認した計画と確認事項の決着は記録に残り、PO が成果の受け入れ確認時に読む。ふりかえりの全結果を PO が事前承認するわけでもない。PO の受け入れ確認で差し戻しとなった場合は、修正・レビューを経て再確認する。図は通常の進行を示し、詳細な戻り方は後続の工程説明で扱う。
