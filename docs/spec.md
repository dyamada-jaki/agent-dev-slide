# agent-dev-slide 仕様

作るもの全体の目的・内容・範囲を定める仕様書。PO が、人間と決めたことを記録する。

## 1. これは何か

`agent-dev-template` の開発プロセスを、人に説明するための日本語スライド。
このスライド自体も同じプロセスに沿い、仕様から小さな Issue を切り出して段階的に制作する。

- 対象読者: AI を使った開発に関心がある開発者。
- 使用場面: 少し長めの LT。
- 持ち時間: 15分程度。
- 伝えたいこと: agent-dev-template の開発プロセスの全体像。

テンプレートや Orca を初めて知る読者にも、登場する役割と作業の流れがつながる説明にする。

## 2. 中身

説明対象の参照元と版は [sources.md](sources.md) に記録する。
元テンプレートが扱う主題は、Spec・Issue・Orca、3つの役割、Issue ごとの8ステップ、人間の判断、レビュー、記録とふりかえり。
LT 全体の構成は、下記の導入を起点に、Issue 1本の流れ、人間の判断と記録、始め方へつなぐ案で検討する。
全体の枚数と章ごとの時間配分は固定せず、計画と通し確認で調整する。

### 2.1 最初に作る部分: 全体像と役割

LT の導入として、表紙と、次の内容を説明できる最初のまとまりを作る。

- 何を説明するか: 人間と AI エージェントが、仕様づくりから実装・レビュー・マージ・ふりかえりまで進めるためのプロセス。
- Spec・Issue・Orca の関係: Spec は作るもの全体の仕様、Issue は今回実装する作業の目的・範囲・受け入れ条件を記すもの、Orca はエージェントの端末と worktree を扱う作業環境。
- 3つの役割: PO は仕様・Issue・受け入れ確認、開発チームは Issue の進行・比較・完了処理、開発者は自分の worktree で実装・レビューを担う。
- 人間の位置づけ: PO と議論し、計画・採用する PR・改善の採否を判断する。エージェントの3つの役割と、人間が担う判断を区別する。

初回は導入に範囲を絞る。8ステップの詳細、起動係の設定手順、個々のスキルの使い方は後続 Issue で扱う。
導入の枚数・レイアウト・口頭で補足する内容は実装計画で提案し、人間の計画承認を経て制作する。

### 2.2 個人用スライドデザインの検討

今後の発表を通じて Overstrata を知ってもらう意図を持ち、作品の雰囲気を取り入れた、個人用の共通デザインを検討する。今回の LT を試用する場にし、後の発表にも再利用できるルールとページの型を段階的に整える。

- ロゴや既存の絵を直接使うことを共通テンプレートの前提にしない。キャラクターが写る既存の絵は説明内容と合わないことが多いため、雰囲気だけを理由に置かない。
- 絵で表現する必要があるときは、説明内容に合う題材を選び、Overstrata の絵の画風を参照して描く。作品の舞台・物語をそのまま持ち込む必要はない。
- 人を表すときは、デフォルメ調のレナ・ヨナを基本の候補にする。もっと人数が必要な場合も、同じデフォルメ調のキャラクターでそろえる。人物表現に写実的な絵を使わない。
- 画風は、淡い水彩、にじみ、紙の余白、控えめな色数、柔らかい光などを参照して検討する。人物の形は上記のデフォルメ調とし、写実性を引き継がない。題材・キャラクター・画風を分けて指定する。
- 初回の表紙・説明・作品紹介の3枚は PDF で人間が確認済み。絵とロゴの直接利用を前提とする案を見直した。その後の導入3枚の比較では、下記のとおり PR #6 を修正の土台に選んだ。正式な共通テーマへの採用は後続 Issue で扱う。
- 本文は直接的な言葉で説明する。作品の絵を使うことを理由に、開発プロセスの用語を作中の言葉や比喩に置き換えない。
- 文字と絵のバランス、日本語の読みやすさ、Overstrata らしさを人間が確認する。配色・書体・サイズ・ページの型の詳細は、確認後に決める。
- 検討用の見本と本編を区別する。正式なテーマへの組み込みと本編への適用は、後続 Issue の範囲・計画を決めて進める。

#### 次に作るもの: 導入を使ったデザイン比較

- Issue #1 で採用した導入6枚（`a69f2e5`）を題材とし、代表3枚を同じ内容で2案作る。別の発表内容は作らない。
- 対象は1枚目「表紙」、3枚目「Spec・Issue・Orca の関係」、5枚目「人間は3つの役割に含めず、判断を担う」。それぞれ、配色・書体・余白、情報と図の読みやすさ、デフォルメした人物の使い方を確かめる。
- 初回比較では両案の対象ページ、説明する情報、用語、発表ノートの意味と出典をそろえる。改行・配置は変えてよいが、デザインの比較を内容の優劣にすり替えない。比較後に人間が選んだ修正は下記に従う。人物は人間を表し、AI エージェントの役割との区別を保つ。
- 比較するのは計2案。通常の二重実装では各開発者が3枚の1案を担当し、両 PR を合わせて2案を比較する。各案について配色・書体・余白・人物表現の意図を示す。
- HTML・PDF の見本と、同じページを見比べる方法を用意する。Orca のブラウザプレビューで確認できるようにする。人間が採用・修正の判断をできる状態までを、この Issue の制作範囲とする。
- 配色・書体などは開発チームの計画で提案し、人間の承認後に見本を作る。最終的なデザインの採用とは分ける。
- この比較を、スクラム用語を追加する Issue #4 より先に進める。スクラム用語の追加、残りのページへの展開、共通テーマの正式実装、本編への適用は別 Issue とする。

#### Issue #5 の比較後に決めた修正方針

2026-10-28、開発チーム（Run `run_801ae3053c85`）から人間の表示比較後の判断を受領した。PR #6 を土台に修正し、PR #7 の金色の強調を取り入れる。

- カード形式を避け、罫線で情報を区切る。人間の原文は「カードはとてもAIっぽさが良くも悪くも出るので、罫線にしてみましょうか。また、下部の１行コメントも無しでいいです。これもAIっぽさがすごい。」。
- 元の5枚目の3つの判断は「金色で強調する」。
- 下部の1行コメントは画面から外して「発表ノートに移す」。対象は元の3枚目「Spec から今回作る部分を Issue に切り出し、Orca で1本ずつ作る」と、元の5枚目「3つの判断は人間が行う。それ以外はエージェントが進める」。この2文の移動を内容維持条件の明示的な例外とし、それ以外の説明情報・用語・ノートの意味と、開発プロセスの出典は保つ。
- 推奨された挿絵の縮小、「役割には数えない」の文字を濃くする修正、元の3枚目の語の途中の改行の解消、CI のフォント確認結果の追記も「一緒に直す」。
- Overstrata については、人間の「Overstrataは私がAIと共に作っている物なので、出典をわざわざ言う必要は無いです。好きに使っていいです。」に従い、絵・キャラクター・画風の出典やクレジットの記載を求めない。使用ファイルと生成・編集した素材の区別は保守用の記録として残す。開発プロセスの説明を裏付ける出典の記録は継続し、未公開資料の本文・生成指示の転載は行わない。
- ヨナについての原文は「よくあれだけの情報でヨナを見つけましたね。すばらしいです。」。開発チームは PR #6 の茶色の巻き毛・暗い色の上着の人物をヨナと認めた発言と解釈している。この解釈と PR #6 の選択を踏まえ、今回の修正は同案の人物表現で進める。作品の正式な外見設定を新たに定義するものではない。
- main に残すのは「#6 だけ」。修正後の再レビュー・受け入れ確認を経て完了処理を行い、PR #7 はブランチを残してクローズする。2案の比較記録は残す。

### 2.3 スクラムの考え方・用語との対比

人間は、この開発プロセスにスクラムの考え方をなるべく取り入れている。その意図を説明するため、スクラムとの対比や用語をスライドに加える。分かりにくい用語には、かっこ書きによる補足も検討する。

- 導入の6枚を対象とする後続 Issue として扱う。Issue #1 の完成済みの範囲と区別する。
- 元テンプレートの役割・手順は固定版で確認し、スクラムの定義は [参照元](sources.md) に追加したスクラムガイドで確認する。
- 着手前に、PO・開発チーム・開発者、Spec・Issue・区切り、ふりかえり、人間の判断をどう対比するか、人間と対応表を決める。呼び方が似ているだけで同一の役割・イベント・作成物だと決めない。
- 用語の補足にとどめるか、共通点・違いまで本文で示すか、かっこ書きの形式と発表ノートへの分担も着手前に決める。

## 3. 決まりごと

- 説明対象と本プロジェクトの運用設定を区別する。説明は参照元で裏付ける。
- スライド本文と発表ノートでは「席・地図・一片・作業票・関所」の比喩表現を使わず、役割・仕様・作業範囲・判断内容を直接説明する。「3つの席」は「3つの役割」と言い換える。
- 元テンプレートが「席」と呼んでいる旨の補足は、発表ノートにも残さない。本文・ノートの可読文には、出典の節名や引用、言い換えの説明としても上記の比喩を再掲しない。出典は固定版のファイル URL などで示し、参照元の意味と対応を保つ。
- 制作は [workflow.md](workflow.md) の Spec → Issue → 計画 → 実装 → レビュー → マージ → ふりかえりに従う。
- 1つの PR は1つの Issue を扱い、人間による計画承認・採用判断・改善の採否を保つ。
- 内容の正しさ、スライド表示、自動確認、人間による通し確認を分けて記録する。
- 制作環境の初期設定は Markdown／Marp、16:9、HTML・PDF 出力。原稿は `slides/index.md`、生成物は `dist/`。これはセットアップ時の暫定選択で、希望があれば本文制作前に変更する。
- 公開してはいけない資料や認証情報を含めない。
