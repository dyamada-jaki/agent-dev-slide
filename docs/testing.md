# テストとレビューの方針

仕様の正本は [spec.md](spec.md)、今回の範囲は GitHub Issue に置く。
このプロジェクトでは、日本語のスライド原稿・HTML・PDF を確認する。

## 1. 制作前に決めること

- 受け入れ条件ごとに「読者が何を理解できるか」「根拠となる参照元」「対象ページ」「確かめ方」を計画に書く。期待結果は仕様と参照元から決める。
- 文書制作なのでテスト先行は「しない」。本文の完全一致を固定するだけのテストは作らない。
- 間違えやすい点を具体化する。例: 人間の承認を自動処理として説明する、PO と開発チームの役割を混同する、日本語の長い見出しが切れる。
- 設定やツールを変更するときは、実際のビルド・起動・出力で変更前後を確かめる。不具合修正は修正前の再現結果を残す。
- 未決の対象読者・説明時間・章立てを実装者の推測で確定しない。

## 2. 確認の層と分担

| 層 | コマンド・方法 | 確かめることと限界 |
|---|---|---|
| 原稿 | `npm run lint` | Markdown の書式。元テンプレートの workflow・ADR 雛形・レポート説明は書式変更を避けるため lint 対象外 |
| ローカル参照 | `npm run check:links` | 原稿・文書の相対リンクや画像の存在。架空の Issue リンクを持つ ADR 雛形は対象外。外部 URL とアンカーは自動確認の対象外で、レビュー時に開いて確かめる |
| ガイド同期 | `npm run check:guides` | CLAUDE.md と AGENTS.md が同一であること |
| HTML | `npm run build` | 原稿が HTML に変換できること。レイアウトや内容の正しさは別途確認する |
| PDF | `npm run build:pdf` | Chrome で PDF に変換できること。日本語フォントとレイアウトは目視でも確認する |
| エージェントの表示確認 | HTML と PDF の全ページ | PC 1280×720 を基準に、文字切れ・重なり・画像欠け・日本語表示・ページ送りを確認する。1ページだけならページ送りは対象外 |
| 人間の確認 | 発表に使う画面で通して読む | 説明の順序、読みやすさ、話す内容との対応、持ち時間内で説明できるか。エージェントの確認と分けて記録する |

`npm run check` で自動確認をまとめて実行する。CI も同じコマンドを使う。
初期原稿の1ページは環境確認用であり、説明資料の完成とは扱わない。
スマホ向けのレイアウトは現時点では対象外。

## 3. 実物と出典で確認する

- 実際の Marp CLI と Chrome で生成する。生成物をモックに置き換えない。
- プロセスの説明は [sources.md](sources.md) に記録した版と突き合わせる。運用用に編集した文書だけを説明対象の根拠にしない。
- 出典 URL は各スライドのノート（HTML コメント）に残し、公開資料から確認できない効果や性能を断定しない。
- 外部 URL の到達と記述内容の一致は、人間またはエージェントがレビュー時に確認する。CI のリンク確認成功だけで出典の検証済みとはしない。

## 4. E2E とミューテーション

どちらも未導入。スライド表示の目視とビルド確認を行う。
操作の自動検証が必要になった場合は、専用 Issue で対象とコマンドを決める。

## 5. PR レビューの分担

レビュー対象は PR の説明や差分だけではない。Issue・仕様を起点に、**変更された原稿・設定と生成物、参照元・関連ページ**まで、影響を判断できる範囲で読む。無関係な箇所まで全リポジトリを精査することは求めない。

| 担当 | 主な責任 |
|---|---|
| 相互レビュー担当 | 受け入れ条件を1つずつ判定し、仕様との一致、バグ・回帰、スコープ、検証の証拠を確認する。対象コミットで必須チェックを再実行する。HTML の変更ページと関連ページをブラウザで確かめ、PDF とも見比べる |
| 独立した品質レビュー担当 | 新しいセッションで、説明の順序、出典との一致、用語の統一、読みやすさ、変更のしやすさを確認する |
| コーディネーター | 指摘を原稿・参照元・仕様・生成物で裏付け、重複・誤検出を整理する。今回直すものと別 Issue の候補を分け、採用判断を人間に示す |
| 人間 | 実機の使いやすさと仕様上の判断を確認し、採用する PR を決める |

品質レビューは、人間が明示的に指定した場合に追加する。PR ごとに実装・相互レビューとは別のセッションを使い、他者のレビュー結論を読む前に自分の確認結果をまとめる。相互レビューとの同時実行は可能だが、別の worktree を使い、同じファイルやコンテナを操作しない。役割名だけで品質が上がったとは判断しない。

### 二重実装と品質レビューの評価

続けるかを判断するときは、二重実装の比較で得た価値と、独立した品質レビューの追加価値を分けて評価する。

- **得られた改善**：具体的に確認できた不具合・回帰・検証不足、採用した設計やテストの観点と、その後の修正・再確認。提案の採用と実装完了を区別し、後続へ引き継いだものも結果を追う。
- **独自性**：どの担当・比較で初めて確認できたか、相互レビューと重複したか。指摘件数をそのまま成果として数えない。
- **手戻りと負担**：誤検出・判断できなかった指摘と、その調査や修正に要した手戻り。担当別の時間と追加待ち時間は6章の方法で記録し、費用・トークン量など未計測の値を推定で補わない。
- **判断**：品質への具体的な寄与を優先し、継続／対象を絞る／終了／材料不足で継続観測の案と根拠を示す。比較するIssueの規模・性質・対象SHAの違いを考慮し、モデル全般の優劣や「担当がいなければ必ず見逃した」といった反実仮想は断定しない。材料不足なら追加で確かめる対象と判断時点を示す。

### 対象コミットと確認結果

- レビュー開始前に PR の `headRefOid` を記録し、作業場所の `HEAD` と一致することを確かめる。相互レビューと品質レビューは同じコミットを対象にする。未コミットの変更があれば、そのままレビューしない。
- 相互レビュー担当は「開発設定」の確認コマンドと、導入済みで対象となる E2E を実行する。品質担当は重複実行を必須にせず、説明の構成と根拠を重点的に読む。実行が必要なら自身の隔離された作業場所で行う。
- 実行できないチェックは、理由と未確認の範囲を記す。CI・実装者の報告・自分で再確認した結果を区別し、未確認を「合格」にしない。
- 修正で head が変わったら、古いレビューはそのまま採用判断に使わない。更新差分と影響範囲を再確認し、新しい SHA と確認結果を残す。修正が不要だった場合も、報告時とマージ前に head が同じか確かめる。

### 指摘の書き方と扱い

1件ごとに、対象 SHA、ファイルと行、発生条件または具体的な影響、根拠（仕様・原稿・参照元・再現結果）、修正案を付ける。確認できない懸念は、事実と分けて「未確認」と書く。

- **必須**：受け入れ条件を満たさない、仕様に反する、再現できるバグ・回帰など、今回の完了を妨げるもの。採用前に解消し、再確認する。
- **推奨**：具体的な保守・変更上の負担やテストの弱点があり、改善する価値があるもの。今回のスコープに必要なら修正し、独立した改善なら後続 Issue の候補にする。
- **好み**：振る舞いや具体的な保守上の影響がない表現上の違い。原則として採用を止める理由にしない。

推測上の将来要件に備えるだけの抽象化や、好みだけの全面改修を求めない。コーディネーターは各指摘を「確認できた／誤り／判断できない」に分け、確認できたものの対応先と、除外した理由を残す。

## 6. 証拠を残す

- **計画**：受け入れ条件と検証方法、仕様から決めた代表例・期待結果、モックを使う場合の理由、E2E の対象または対象外の理由。
- **PR**：対象コミット、実行コマンド・環境・結果、HTML・PDF の対象ページ・画面の幅・操作・結果、未確認の条件。期待値を変更した場合は根拠も残す。
- **ミューテーションテスト**：導入済みで対象となる場合は、実行範囲・結果・生き残った変異の判断と対応先をPRに残し、レビューとIssueレポートへ引き継ぐ。
- **レビュー**：担当と役割、対象 SHA、読んだ原稿・参照元・設定の範囲、自分で実行した確認と他者の証拠、指摘と残る不確実性。
- **[Issue レポート](issue-reports/README.md)**：両レビューの結果とリンク、コーディネーターの確認、修正後の再確認、採用理由。品質レビューを加えたときは、相互レビューと重複しなかった有効な指摘、誤検出と除外理由、追加の所要時間も残し、続けるかの判断材料にする。時間を測れなければ推定値で埋めず「記録なし」とする。

所要時間は担当ごとの開始・終了時刻で記録する（finish-issue が作業時間の表を作る）。「追加待ち時間」は相互レビューがそろってから品質レビューがそろうまでの時間とし、品質レビューが先に終わっていれば0とする。
