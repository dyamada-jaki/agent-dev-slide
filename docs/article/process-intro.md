# AI エージェントとの開発に、スクラムの役割とイベントを取り入れてみた

agent-dev-template という、AI エージェントと一緒に開発を進めるためのテンプレートを GitHub で公開しています。人間が判断し、Claude Code と Codex が仕様づくりから実装、レビュー、マージ、ふりかえりまでを進める。そのための役割分担と手順を、ひとまとめにしたものです。

この記事では、このテンプレートでの開発の進め方を紹介します。どんな役割があり、1つの Issue がどんな順番で進み、どこで人間が判断するのか。あわせて、なぜこういう形にしたのかも、作った本人として書いておきます。

設計するときに意識したのは、スクラムの役割とイベントをできるだけ取り入れて、このプロセスの中でスクラムが実践されている状態を作ることでした。ただ、正しいスクラムをそのまま再現したわけではありません。スプリントの期間は決めていませんし、デイリースクラムもありません。何を取り入れて、何を取り入れなかったのかも順に説明します。

## 作ろうとしたもの

agent-dev-template は GitHub のテンプレートリポジトリで、新しいリポジトリの土台としてコピーして使います。中に入っているのは、エージェント向けのガイド（Claude Code 用の CLAUDE.md と、Codex 用の同じ内容の AGENTS.md）、Issue の実装や完了処理の手順をまとめたスキル、仕様書や記録の雛形などです。既定は Web アプリ向けの設定ですが、設定と確かめ方の方針を書き換えれば、スライドや文書の制作にも使えます。

進め方の土台になるのは、仕様書と GitHub の Issue です。仕様書（docs/spec.md）には、作るもの全体の目的や範囲、決まったことと未決のことを書きます。Issue には、その中から今回作る分だけを切り出して、目的、範囲、受け入れ条件（完成とみなす条件）、やらないことを書きます。仕様書はずっと育てていき、Issue は1本ずつ終わらせていく、という分け方です。

エージェントは Orca というアプリの上で動かします。Orca は、複数の AI エージェントの端末と、Git の worktree（1つのリポジトリから作業用のフォルダを複数取り出して並べる仕組み）をまとめて扱えるアプリです。後で説明するように、このプロセスでは複数のエージェントが同時に別々の作業場所で動くので、それをまとめて見られる環境を前提にしています。

この記事で伝えたいのは、スクラムそのものの解説ではありません。スクラムのイベントなどを、形を変えながらこの開発プロセスに取り込んでいる。その取り込み方を、実際の役割と流れに沿って説明するのが目的です。

## 登場する役割

このプロセスに登場する AI エージェントの役割は、PO（プロダクトオーナー）、開発チーム、開発者の3つです。そこに人間が加わります。まず、それぞれが主に何をするかを並べておきます。表に出てくる PR（プルリクエスト）は、GitHub で変更をまとめて、レビューと取り込みを依頼する仕組みです。

| 担当 | 主にすること |
|---|---|
| 人間 | 作る方向と優先順位を PO と相談して決める。計画、成果、改善案を確かめて判断する |
| PO（AI） | 人間と優先順位を検討し、仕様と Issue に整理する。成果を受け入れ条件と照らして確認する |
| 開発チーム（AI） | Issue ごとの進行を管理し、2つの実装案を比べる。採用が決まったらマージと後片付け、ふりかえりを行う |
| 開発者（AI） | 同じ Issue を2人が別々に計画、実装、検証し、互いの PR をレビューする |

人間は AI の役割には数えていませんが、役割がないわけではありません。後で説明する計画、成果の確認、ふりかえりのそれぞれに人間が入っているので、私は人間をステークホルダーであり、一部 PO の役割も担う存在だと捉えています。AI の PO は、人間との議論を仕様や Issue、着手の順番に整理し、成果の受け入れ確認を進めます。スクラムの PO の責任をすべて AI に移したわけではなく、作る方向や優先順位を決めるのは人間です。

PO と開発チームを別の役割にしたのには理由があります。1つの端末に両方をまとめると、会話の文脈がすぐにあふれてしまい、開発を進めている最中にプロダクトについての検討を進めにくくなるからです。そこで PO は長く使い続ける端末にして、状態は仕様書などのファイルに残し、いつ開き直しても続きから始められるようにしました。開発チームのほうは Issue ごとに開いて、その Issue のふりかえりが終わったら自分で閉じます。

開発チームという名前についても少し書いておきます。この役割は、Issue の進行を主導する性格がかなり強いので、私にはスクラムマスターという感じではないように思えました。それで「開発チーム」と名付けています。私の感覚では、このプロセスにスクラムマスターはいません。強いて言えば、開発チームの中にスクラムマスターの要素も入っている、という程度です。開発チームをスクラムマスターの言い換えとして読まないでもらえると、以降の説明が分かりやすいと思います。

開発者は Claude Code と Codex が1人ずつです。この記事で紹介する進め方では、同じ Issue を2人が別々に作り、互いにレビューし、開発チームがどちらを採るかを推薦します。ただし、テンプレートの手順書では2つのエージェントで作って比べることを任意としていて、1人で1つの案を作る使い方もできます。比べる理由として、手順書には、2つの作りの違いから仕様の抜けや両方に足りない点が見つかりやすい、と書いています。

図の上の段にいるのが人間と AI の PO で、2人の対話から GitHub の Issue が作られます。Issue に「開発可」のラベルが付くと、下の段の流れが始まります。下の段は、計画、実装と検証、成果の確認、ふりかえりの順に進み、開発チームがこの流れ全体を管理します。図で人間の判断として強調しているのは、計画の承認、成果の採用、改善案の採否のところです。ふりかえりの結果は AI の PO に申し送られ、次の仕様や Issue に反映されて、また上の段の対話に戻ります。

スクラムには期間を区切ったスプリントがありますが、このプロセスでスプリントという固定の期間を作ることはできませんでした。その代わり、Issue 1本の計画から実装、確認、ふりかえりまでを、スプリントの流れを踏襲するように意識して組み立てています。以下では、その流れを、スクラムのイベントと関連する活動として5つに分けて説明します。

### リファインメント

最初は、やりたいことを仕様と Issue にする段階です。人間がやりたいことを AI の PO に話し、2人で相談しながら、作る方向と優先順位を決めます。PO はその結果を仕様書に書き、今回作る範囲を Issue に切り出します。Issue には目的、範囲、受け入れ条件を書き、スクラムでいうプロダクトバックログアイテム（PBI）の代わりとして扱っています。

着手の順番は、人間と相談して決めた優先順位をもとに、PO が具体的に決めます。PO が Issue に「開発可」のラベルを付けると、開発チームが起動します。起動するのは Orca の定期実行で、15分おきに「開発可」の Issue があるかを確かめ、動いている開発チームがいないときだけ開発チームの端末を開きます。開発チームは同時に1つまでなので、Issue は基本的に1本ずつ進みます。

スクラムでは開発者もリファインメントに加わりますが、このプロセスでは人間と AI の PO が中心で、開発者はこの次のプランニングから加わります。

### プランニング

開発チームが起動すると、開発者2人がそれぞれ同じ Issue を読み、すぐにはコードを書かずに、自分の計画を立てます。受け入れ条件をどう満たすか、何をどう確かめるか、仕様から読み取れずに確認したいことは何か、といった内容です。開発チームは2つの計画と確認したいことをまとめて人間に示します。

人間は、計画を自分が作りたいものと照らして確認し、必要なら調整して承認します。小さな疑問ならその場で答えますが、答えることが仕様を決めることになるような穴が見つかった場合は、実装を止めて PO に戻し、仕様と Issue を直してから進め直します。テンプレートの手順書には、Issue の曖昧さは計画に表れるので、コードになる前に見つけるのがいちばん安い、という理由を書いています。人間が承認すると、開発者2人はその計画でそれぞれ実装に進みます。

### 開発

承認された計画に沿って、開発者2人がそれぞれ自分の worktree で実装し、確認のコマンドを通して検証し、PR を出します。PR の本文には、何をしたか、どう確かめたか、確認したいことを書きます。2人は互いの PR をレビューし、開発チームが2つの案とレビューの結果を受け取って比べ、推薦する PR を選びます。

承認された計画に沿って進む開発には、人間の作業はありません。実装、検証、相互レビューは AI が進めます。ただ、途中で仕様の不足が見つかって判断が必要になれば、作業を止めて PO や人間に戻します。人間に一切相談しないという意味ではなく、計画で合意した範囲の作業は AI に任せる、という分け方です。

### レビュー

開発者どうしのレビューを終えた成果を、AI の PO、人間の順に確かめます。開発者どうしのコードレビューは開発の中の作業で、ここでいうレビューは成果の確認です。

まず、開発チームが推薦した PR を、AI の PO が受け入れ確認します。PO はコードを見ずに、受け入れ条件や仕様、スコープ、使う人から見た振る舞いと照らして判断します。差し戻しになれば開発チームが直して再確認し、差し戻しは2回までで、3回目は人間に判断を仰ぎます。

PO が受け入れたら、人間が実物を確かめます。そのうえで、採用するか、修正が必要か、受け入れ条件そのものを見直すかを決めます。条件を見直すときは、PO と一緒に仕様と Issue を直します。採用が決まり、人間が実行内容を承認すると、開発チームがマージし、採らなかった PR を理由を残して閉じ、worktree などの後片付けをします。

AI の PO の受け入れ確認は、あくまで人間の判断の前の確認です。採用を決めるのは人間で、私は、この人間による成果の確認でスプリントレビューを実践できていると考えています。

### ふりかえり

採用した成果を取り込んだあと、開発チームが Issue 1本の進め方をふりかえります。検証やレビューの記録、作業ごとの開始と終了の時刻の表などから、続けること、改善すること、時間のかかった作業などを整理し、根拠のある改善案を示します。改善案には、どこに反映するか、どんな効果を期待し、それをどう確かめるかを付けます。

人間は改善案ごとに採否を判断します。採用された改善は、開発チームが手順書やスキルなどに反映します。仕様についての発見や次の Issue の案は、開発チームが PO に申し送り、PO が人間と相談して次の仕様や Issue に反映します。ここから次のリファインメントにつながります。

改善を採用したこと、手順に反映したこと、その効果を確かめたことは、それぞれ別のこととして扱います。反映した改善が役に立ったかどうかは、次の Issue で確かめます。ふりかえりが終わると、開発チームは自分の端末を閉じます。次に「開発可」の Issue があれば、Orca の定期実行がまた開発チームを開きます。

## スクラムとの対応と、取り入れていないもの

ここまでの内容を、スクラムの用語と対応させると次のようになります。対応はこのプロセスでの取り入れ方を説明するためのもので、スクラムの定義と同じものだという意味ではありません。

| スクラムの用語 | このプロセスでの扱い |
|---|---|
| プロダクトオーナー | 人間が方向、優先順位、採用を判断し、AI の PO が仕様、Issue、着手の順番に具体化して受け入れ確認を進める |
| スクラムマスター | 独立した役割としては置いていない |
| 開発者 | AI の開発者2人（Claude Code と Codex） |
| スプリント | 期間は設けず、Issue 1本ごとにスプリントの流れを踏襲する |
| スプリントプランニング | 開発者の計画を、人間が確認、調整して承認する |
| デイリースクラム | 取り入れていない |
| スプリントレビュー | AI の PO の受け入れ確認のあと、人間が成果を確かめて採用を判断する |
| スプリントレトロスペクティブ | 開発チームの改善案を、人間が採否を判断して手順に反映する |
| プロダクトバックログアイテム | GitHub の Issue |

取り入れられなかったものもあります。スプリントの固定期間は、Issue ごとに流れを回すこのプロセスでは作れませんでした。デイリースクラムも、このプロセスには含めることができなかったと認識しています。進捗の通知などをデイリースクラムの代わりとして扱うこともしていません。スクラムマスターは、先に書いたとおり独立した役割としては置いていません。

人間が判断する場面は、計画の承認、成果の採用、改善の採否の3つが中心ですが、それだけではありません。リファインメントでは PO と一緒に方向と優先順位を決めますし、計画や確認の途中で仕様についての質問が来れば答え、必要なら条件を見直します。AI に任せているのは、合意した計画の範囲での作業です。

## 記録の残し方

このプロセスでは、判断の内容を GitHub に残します。開発チームの推薦や PO の受け入れ判断は PR のコメントに書き、エージェントの端末どうしのやりとりは合図だけにしています。Issue ごとの計画、承認、検証、採用の理由、改善の反映先は、Issue レポートという1本の Markdown ファイルにまとめます。

会話はいずれ消えますが、仕様書は残ります。PO は会話の記憶を引き継がないので、経緯は仕様書や現在地の記録（今どこまで進んだかと次に切る Issue をまとめた文書）、Issue に書いておき、開き直したら最初に読ませます。PO と開発チームは同じ作業場所で動くので、仕様書や現在地の記録は PO だけが書き、開発チームは Issue レポートとコメントで PO に申し送る、というように役割ごとに書くファイルを分けています。同じファイルを同時に書き換え合わないようにするためです。
